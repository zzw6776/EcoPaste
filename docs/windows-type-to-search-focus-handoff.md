# Windows 唤起后直接输入搜索的焦点交接设计

> 状态：问题已确认，方案待实现。本文记录根因、约束、推荐实现与验收范围，不表示当前版本已经具备该能力。

## 问题描述

macOS 上通过全局快捷键唤起剪贴板窗口后，即使搜索框尚未展开，用户直接输入普通字符也会自动展开搜索并保留首字符。Windows 上相同操作不会进入搜索，字符可能继续发送给唤起前的前台应用。

当前仍可通过点击搜索按钮，或开启“打开窗口时聚焦搜索”后直接输入。它们只绕过了首字符焦点交接问题，不是跨平台体验一致的最终实现。

## 当前链路

### macOS

`src-tauri/src/window/macos.rs` 把剪贴板窗口转换为非激活 `NSPanel`，允许它成为 Key Window，并在显示时调用 `show_and_make_key()`。因此应用不需要进入普通主窗口激活流程，WebView 仍可以收到原生键盘和输入法事件。

前端 `src/pages/Clipboard/components/List.tsx` 收到单字符 `keydown` 后发送 `ecopaste:type-to-search`，`Header.tsx` 展开搜索框、写入首字符并聚焦输入框。

### Windows

`src-tauri/src/window/windows.rs` 在显示剪贴板窗口前强制设置 `focusable=false`，以保留原应用作为粘贴目标。不可聚焦窗口无法通过 WebView 收到普通键盘输入。

`src-tauri/src/keyboard/windows.rs` 使用 `WH_KEYBOARD_LL` 捕获窗口可见期间的系统键盘事件，但只向前端转发导航键、空格和选定的 Ctrl 快捷键，没有转发普通文本输入。于是前端的 `ecopaste:type-to-search` 逻辑在 Windows 上没有字符事件可以触发。

搜索框被显式聚焦时，`src/hooks/useClipboardWindowEditableFocus.ts` 会调用 `set_clipboard_window_editing(true)`。Rust 随后保存原前台窗口、停止导航钩子、把剪贴板窗口设为可聚焦并聚焦它；输入结束后再恢复不可聚焦状态和原前台窗口。这条链路能够正常输入，但缺少从“第一个普通字符”进入该链路的安全入口。

## 根因

这是新增“直接输入搜索”交互后未补齐的 Windows 平台适配，不是搜索查询或输入框状态更新故障。

Windows 没有与 macOS 非激活 `NSPanel` 完全对等的窗口机制。当前产品同时要求：

- 唤起剪贴板窗口时不抢走原应用焦点。
- 未编辑时可以用方向键、空格和快捷键操作列表。
- 直接输入时支持完整的原生输入法，并且首字符不丢失。
- 选择记录后把模拟粘贴发送回原应用。

在 Windows 上，不可聚焦窗口不能接收原生文本输入；一旦为了输入而激活剪贴板窗口，又必须可靠保存和恢复原粘贴目标。因此需要显式的焦点交接，而不能只依赖浏览器事件。

## 不采用的方案

### 直接把虚拟键码转换成字符

低级键盘钩子拿到的是虚拟键码、扫描码和按下/松开状态，不是输入法提交后的文本。直接把 `VK_A` 等映射成字符会破坏中文输入法、非英文键盘布局、死键、Shift 符号和组合输入。

### 只向前端发送首字符事件

这会绕过系统输入法，且从 Rust 到 WebView 的异步事件无法保证后续快速输入的顺序。若不吞掉原事件，字符还会同时落入背后的应用；若吞掉但焦点切换失败，首字符就会丢失。

### 唤起时始终聚焦搜索框

这是实现最简单且能够使用原生输入法的方案，但会把“打开窗口时聚焦搜索”从可选行为变成固定行为，并破坏 Windows 剪贴板窗口默认不抢焦点的现有契约。除非产品明确决定改变该交互，否则不作为根因修复。

## 推荐方案

实现 Windows 专用的“首字符焦点交接”，只在检测到用户有文本输入意图时临时激活搜索框。低级钩子只负责保存和重放物理按键，不自行解释最终字符，字符生成仍交给 Windows、输入法和 WebView。

### 状态模型

```text
Navigation
  剪贴板窗口不可聚焦；现有导航键钩子工作
      |
      | 检测到文本输入意图
      v
SearchHandoff
  暂存并吞掉交接期间的物理按键；只发送一次聚焦请求
      |
      | 搜索框确认获得原生焦点
      v
Editing
  停止全局键盘拦截；重放暂存按键；后续输入走 WebView/IME
      |
      | 输入框失焦、窗口隐藏或取消搜索
      v
Navigation
  恢复不可聚焦窗口、导航钩子和原前台窗口
```

同一时间只能存在一个交接会话。每个会话需要唯一 ID，避免旧的异步确认完成后错误地重放到新的搜索会话。

### 交接流程

1. Windows 键盘钩子在 `Navigation` 状态检测无 Ctrl、Alt、Win 修饰的潜在文本按键。Shift 和 Caps Lock 只作为物理键状态保留，不在钩子里计算字符。
2. 钩子切换到 `SearchHandoff`，吞掉原始事件并按顺序缓存按下、重复和松开事件，避免它们进入背后的应用。
3. Rust 向剪贴板窗口发送一次搜索聚焦请求。前端收到后展开搜索框，并通过窗口命令进入可编辑状态。
4. 搜索框调用原生 `focus()` 后，前端同时验证 `document.activeElement`，再携带会话 ID 确认焦点交接完成。
5. Rust 校验会话仍有效且剪贴板窗口确实位于前台，然后停止交接拦截，通过 `SendInput` 按原顺序重放缓存的扫描码事件。
6. 重放事件需要带可识别的注入标记，低级钩子必须忽略自己的重放事件，避免递归捕获。
7. Windows 输入法和 WebView 在已经聚焦的搜索框中原生处理重放事件；后续按键不再经过全局导航逻辑。
8. 搜索框失焦或窗口隐藏时，复用现有 `editing=false` 链路恢复不可聚焦状态、导航钩子和原前台窗口。

### 并发与失败处理

- `SearchHandoff` 的缓存必须有容量和时间上限，避免前端无响应时无限吞键或增长内存。
- 焦点确认超时、窗口隐藏、会话 ID 不匹配或前台窗口校验失败时立即取消会话并清空缓存。
- 失败时不得把缓存内容发送给未经校验的窗口，避免敏感输入泄漏到错误应用；应恢复导航状态并记录可诊断日志。
- 快速连续输入时，交接期间的全部按下、重复和松开事件必须保持原始顺序，不能只保存第一个字符。
- 如果 Shift 的按下事件已经放行给原前台应用，交接时必须先为原应用补齐配对状态，再在搜索框获得焦点后重建仍处于按下状态的 Shift；不能让按下和松开分别落到两个窗口而造成粘滞修饰键。
- 切换到 `Editing` 与停止交接拦截之间不能留下按键既未缓存、又尚未能进入 WebView 的空窗。
- 窗口隐藏和应用退出必须能够无条件结束交接状态，不能遗留全局吞键。

## 预计改动范围

- `src-tauri/src/keyboard/windows.rs`
  - 增加搜索交接状态和有限按键缓冲。
  - 区分真实事件与本应用通过 `SendInput` 重放的事件。
  - 在交接期间完整消费配对的 keydown/keyup。
- `src-tauri/src/keyboard/mod.rs`
  - 集中维护新的事件名与交接入口。
- `src-tauri/src/window/windows.rs`
  - 提供两阶段的可编辑焦点准备和确认能力。
  - 继续复用已有前台 HWND 保存与恢复逻辑。
- `src-tauri/src/commands/window.rs` 与 `src-tauri/src/lib.rs`
  - 暴露焦点确认或取消命令，并保持命令层只做校验与转发。
- `src/constants/events.ts`、`src/constants/commands.ts` 与 `src/commands/index.ts`
  - 同步跨端事件和命令常量。
- `src/pages/Clipboard/components/Header.tsx` 与 `SearchInput.tsx`
  - 响应搜索交接请求，在输入框真实聚焦后确认会话。
- `src/hooks/useClipboardWindowEditableFocus.ts` 与 `useKeyboardEvent.ts`
  - 协调交接态与普通编辑态，避免同一事件被浏览器和 Rust 重复处理。

最终实现应根据实际调用关系保持最小改动；以上是职责边界，不要求为了形式拆出新的抽象。

## 验收范围

### 自动验证

- 状态机覆盖 `Navigation → SearchHandoff → Editing → Navigation` 正常路径。
- 重复聚焦请求不会创建多个会话或重复重放。
- 旧会话确认、焦点失败、超时和窗口隐藏能够取消缓存。
- 注入事件不会被钩子再次缓存。
- 快速输入的 keydown、repeat、keyup 顺序保持不变。
- 前端只在搜索框确实成为 `document.activeElement` 后确认。
- macOS 键盘与搜索链路不受 Windows 分支影响。

### Windows 真机验证

- 从浏览器、Office、VS Code、资源管理器和聊天输入框唤起后直接输入，首字符不进入原应用。
- 英文大小写、数字、Shift 符号和常用非英文键盘布局输入正确。
- 微软拼音等中文输入法能够正常显示候选、组词、提交和退格。
- 快速连续输入、长按重复键和输入期间切换输入法不会乱序或卡住键盘。
- 方向键、空格预览、Enter 粘贴、Escape 关闭和现有 Ctrl 快捷键保持可用。
- 搜索取消、输入框失焦和窗口隐藏后，原应用恢复焦点并能继续输入。
- 非固定与固定窗口下的自动粘贴均发送到原目标应用。
- 焦点交接失败或窗口在交接中被关闭时不向其他应用泄漏缓存内容。
- 普通权限与管理员权限应用的边界行为有明确结果；UAC 安全桌面不作为可绕过范围。

## 完成标准

只有在 Windows 真机确认“首字符不丢失、不泄漏，输入法原生可用，粘贴目标可恢复”后，才能认为该问题已修复。仅让英文字母进入搜索框，或仅在启用“打开窗口时聚焦搜索”时可用，都不满足本文目标。
